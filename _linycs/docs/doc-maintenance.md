# 代码文档维护机制

本规则适用于 `AGENTS.md` 登记的受维护文档。规则文档本身不受普通代码变更维护，只有维护机制发生变化时才修改。

## 1. 文档自身声明

每份受维护文档必须在标题后声明：

- 本规则的链接；
- 管辖范围，即哪些仓库路径的变化可能使文档过时；
- 更新条件，即达到什么语义变化水平时需要修改正文。

文档不保存固定 commit hash。“本文档 commit”统一指该文档在当前分支历史中最后一次实际修改的 commit：

```bash
git log --follow -1 --format=%H -- <document_path>
```

## 2. 检查时机

以下时机必须执行 freshness 检查：

1. 读取文档开头的维护信息后、继续读取并准备依赖正文之前；
2. 修改其管辖范围内的代码之后；
3. 直接修改受维护文档本身时；
4. 相关工作结束或准备提交之前。

首次只读取标题后的维护信息以取得管辖范围和更新条件。读取检查用于判断正文能否作为当前代码事实；修改后检查用于决定是否需要同步正文。

## 3. 检查范围

设文档路径为 `<document_path>`，文档声明的管辖路径为 `<scope...>`。

首先取得本文档 commit，并确认它仍是当前 `HEAD` 的祖先：

```bash
git log --follow -1 --format=%H -- <document_path>
git merge-base --is-ancestor <document_commit> HEAD
```

然后同时检查以下变化，不能只检查已提交内容：

```bash
# 文档上次修改后已经提交的变化
git diff <document_commit>..HEAD -- <scope...>

# 当前已暂存但未提交的变化
git diff --cached -- <scope...>

# 当前未暂存的变化
git diff -- <scope...>

# 当前未跟踪文件
git ls-files --others --exclude-standard -- <scope...>
```

可以先查看 `--name-status` 或 `--stat`，但最终判断必须阅读足以理解语义影响的 diff 和相关代码，不能只依据文件数量或行数。

## 4. 更新判断

- 变化达到文档自身声明的更新条件：同步修改文档，使其描述当前 `HEAD` 加当前工作区的目标代码状态。
- 变化未达到更新条件：不修改文档，也不添加日期、空格或 commit 标记来刷新 Git 记录。
- 不能确定是否影响文档：继续检查相关调用链、配置和数据契约；仍无法确定时再向用户说明不确定点。

因此，“文档 commit 早于 `HEAD`”只表示需要检查，不自动表示文档已经过时。

任何受维护文档一旦进入提交，就视为对其声明范围和整份正文完成了核对。即使本次原本只想修改链接、格式或局部措辞，也必须先完成 freshness 检查并同步发现的其他过时内容，避免一次局部编辑错误刷新文档基线。

## 5. 异常情况

- 文档没有 Git 历史：对管辖范围做一次完整核对，建立首个基线版本。
- 仓库首次引入本维护机制：不信任此前的文档 commit 是否代表完整核对，对每份受维护文档执行一次完整基线检查。
- 文档 commit 不是当前 `HEAD` 的祖先：可能发生了 rebase、跨分支迁移或历史改写，不能依赖增量 diff，必须完整核对文档与当前代码。
- 文档在当前工作区也被修改：仍以最后一次已提交的文档 commit 为比较起点，同时检查当前文档改动是否已经覆盖所有相关代码变化。
- 管辖范围本身不完整：先修正文档开头的管辖范围，再按新范围重新检查。

## 6. 授权与提交语义

用户明确授权修改管辖范围内代码时，必要的文档同步视为同一任务的附属维护动作，不再单独请求授权；这不会授权修改无关代码、运行程序或维护未登记文档。

文档与导致其更新的代码应尽量进入同一 commit。若文档内容无需变化，则保留其旧 commit，由后续读取者按本规则继续增量检查。
